<p>「我们十几个人用 Claude，代理到底买几条并发够？」这个问题每周都会被问一次，但答案从来不在人数里。同一个人一天可能只发几十条消息，也可能挂着一个批量脚本跑整夜；真正决定并发数的是三个量：同时活跃的会话数、单次请求占住连接多久、失败重试额外吃掉多少。下面从一个真实的下午卡顿讲起，把这三个量逐个量出来，再换算成采购单上的端口数和账号数。</p>

<h2>一、先把「并发」拆成三个能数的量</h2>
<p>供应商报价单上写「5 并发」，你心里的 5 和它写的 5 经常不是一回事。签合同前把三个量分开说清楚：会话并发、请求并发、账号并发。混在一起谈，压测那天很容易对不上账。</p>

<h3>会话并发：同一秒有几条连接在等回复</h3>
<p>这是最接近直觉的定义，同一时刻处于活动状态的连接数。浏览器开三个标签页问 Claude，再加一个桌面客户端，就是四条。在代理机上用 ss -s 看 established 的数量，或者 netstat -an 里数一下，比拍脑袋准。注意流式回复走的长连接会一直占着，哪怕你已经切走去看别的页面。</p>

<h3>请求并发：一个登录态里同时挂几条流式请求</h3>
<p>Claude 的回复是逐字出来的，一条消息从发到收完可能十几秒，长文能拖到一两分钟。等回复的时候又开新对话，一个登录态下就有两条请求并行。写脚本时更容易超：循环里没等上一条结束就发下一条，并发数会瞬间翻几倍，而你在监控上只看到「整体变慢了」。</p>

<h3>账号并发：同一个出口上挂几个登录态</h3>
<p>这条最容易被忽略。出口侧看到的不是「五条连接」，而是「五个账号在同一个地址上活动」。长期账号这个数字通常压到 1 至 2 更稳妥；多人共用一个出口的小团队，要把账号并发和连接并发分开记账，否则月底续费时算不清是谁把出口用脏了。</p>

<h2>二、下午三点的卡顿，是最好的峰值样本</h2>
<p>别用平均值得出结论。工作日 14:00 到 17:00 是大多数团队的使用高峰，周末晚上则取决于有没有人加班跑脚本。挑一个「大家都说卡」的时段，把网关日志按分钟拉出来，看连接数和响应时间两条曲线的拐点落在哪一格。</p>
<img src="/tp.png" alt="代理网关控制台按分钟查看连接数与响应时间的监控曲线">
<p>拐点之前的连接数就是你的真实峰值。如果拐点出现在 8 条，那买 8 条只是刚好够用，没有任何缓冲；只要多一个人开第二个标签页，排队就开始了。工程上常用 1.3 到 1.5 的余量系数，落到 8 条上是 10 到 12 条。</p>

<h3>把「变慢」和「排队」分开看</h3>
<p>响应时间上升有两种原因：链路本身拥塞，或者连接池满了在排队。前者表现为首字节时间变长但吞吐没掉；后者表现为请求在本地等待，代理侧看不到对应流量。在网关上加一个排队等待时长的指标，两者一眼能分开，否则很容易误判成「这条 IP 不行了」而去买新的。</p>

<h3>周末和月初的第二个峰</h3>
<p>做订阅类业务的团队还有一个月初峰：续费、对账、批量导出集中在头两天。这个峰往往比日常高 30% 到 50%，且集中在几个小时里。按日常峰值买，月初必然排队；按月初峰买，其余二十多天在浪费。折中做法是保留一小批可按小时追加的弹性端口，只在月初开。</p>

<h2>三、重试策略会把估算放大 1.5 到 2 倍</h2>
<p>很多人算并发时只算正常请求，忘了失败重试。一次请求超时后重发，原连接可能还没释放，新连接又建起来，瞬时占用是两条。超时设置越短、重试次数越多，放大倍数越高。</p>

<h3>超时不要设得太激进</h3>
<p>长文生成本身就要几十秒，把读超时设成 10 秒，等于人为制造大量重试。经验值是把读超时放在 90 到 120 秒，连接超时 5 到 8 秒；重试只对 429、502、503 和连接类错误生效，对 400 这类参数错误重试没有意义，只会白白占住并发。</p>

<h3>退避要带抖动</h3>
<p>固定间隔重试会在同一秒制造一批新连接，把刚缓过来的出口再打满。用指数退避加随机抖动，比如 1 秒、2 秒、4 秒各加 0 到 500 毫秒随机量，最多三次。这一条改完，不少团队会发现原来买的并发其实够用，只是被重试吃掉了。</p>

<h2>四、账号并发和连接并发要分开买</h2>
<p>这两件事在计费上经常被打包成一个「并发数」，实际约束完全不同。连接并发受端口和带宽限制，可以靠加钱解决；账号并发受出口 IP 的条数限制，加钱也未必能马上拿到干净地址。谈的时候分别问：这个套餐给几条独立出口、单条出口建议挂几个账号。</p>

<h3>一个出口挂多个账号的代价</h3>
<p>同一个出口上有多个登录态活动，平台侧看到的是这些账号共享同一网络身份。对需要长期稳定的账号来说，这种共享会削弱「这个号有自己的使用习惯」这件事。真要多账号，宁可多买几条便宜的单 IP 出口，也不要把五个号塞进一条里。</p>

<h3>连接数上限要写进合同</h3>
<p>有的套餐按「并发连接」卖，但实际在网关上限了每 IP 200 条 session，超出直接丢包。这种限制宣传页不会写，测试时用一个简单脚本开 300 条长连接就能验出来。签之前问清楚单 IP 的连接上限，以及超限是排队还是直接拒绝。</p>

<h2>五、把数字写进采购单和监控</h2>
<p>估算的终点不是一句「大概 10 条」，而是一张能被运维直接执行的表：每个业务分组几条出口、每条出口挂几个账号、告警阈值定在哪。表里每一项都要有对应的监控指标，否则三个月后没人记得当初为什么买这个数。</p>

<h3>三条必要的告警</h3>
<p>连接数超过峰值 80% 持续五分钟、排队等待中位数超过 3 秒、单出口 429 比例超过 5%，这三条覆盖了绝大多数容量问题。阈值不要照抄别家，用自己过去两周的数据算分位数，取 P95 再上浮两成。</p>

<h3>扩容的触发条件提前定</h3>
<p>写清楚「连续三天触发容量告警就加购」这样的规则，比每次临时开会讨论省事。加购周期通常按天到按周计，临时抱佛脚往往只能买到共享池，反而把账号环境弄乱，省下的钱又赔回去。</p>

<h2>常见问答</h2>
<h3>五个人共用一条 5 并发的住宅 IP 够不够？</h3>
<p>答：看使用方式。纯手工对话、每人同时开一个窗口，5 条通常够；如果有人跑脚本或习惯开多个标签页，按每人 1.5 到 2 条估更稳。另外要确认「5 并发」指的是连接数还是账号数，两者含义差别很大。</p>

<h3>并发买多了能退或者改小吗？</h3>
<p>答：多数供应商按自然月计费，中途降配要等下个周期，升配可以当天生效。买之前问清最小计费周期和降配规则，短期项目优先选可按小时或按天追加的形态，别一上来就签年付。</p>

<h3>流式回复算一条连接还是多条？</h3>
<p>答：一次流式回复在传输层通常是一条长连接，但浏览器可能同时开预连接和心跳。按 1.2 到 1.5 倍折算比较接近实际，具体以代理机的 established 计数为准，别按「一条消息算一条」硬套。</p>

<h3>换成机房 IP 是不是并发能开更高？</h3>
<p>答：连接数上限确实可能更高、单价更低，但机房段在平台侧的类型判定与住宅不同，长期账号的稳定性未必更好。并发能力和出口类型是两件事，先确认账号能不能承受，再谈能开多少连接。</p>
